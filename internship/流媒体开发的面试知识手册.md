你的主线是：**网络与 C++ 基础 + 时间同步与测量 + 系统故障定位，向 Go/WebRTC 后端迁移。**没有完成的 Go/SFU 实验不要说成已有项目经验。

优先顺序：

- **P0，先掌握：**建连、RTP/RTCP、SFU、弱网、Go 并发、Linux 网络、时钟与排障。
- **P1，再展开：**编解码细节、转码录制、SFU 部署、K8s 和观测。

### 回答问题的固定结构

“它解决什么问题 → 用什么机制 → 什么情况下失效 → 怎么验证。”

例如：jitter buffer 用于吸收包到达抖动，靠有限等待和重排提高连续性；缓存太深会增加延迟，缓存太浅会增加迟到丢弃；我会同时看缓冲等待时间、迟到丢弃率和播放卡顿。

### 01. 流媒体后端与普通 HTTP 后端有什么不同？P0

**简答：**除了业务请求正确，还要连续传输带时间约束的媒体，处理带宽、丢包、抖动、播放期限和有状态会话。很多媒体数据晚到后价值下降，不能依靠无限重试和排队解决。

**追问展开：**HTTP 接口也可能是长连接、流式和低延迟，不能按“有没有长连接”简单区分。RTC 后端的特殊点是媒体时序、实时反馈、码率适配、按流路由，以及端到端质量。

**容易失分：**只回答“高并发”。面试官会继续问：并发连接、活跃发布流、订阅流、转发带宽，究竟哪个先成为瓶颈？

## 2. WebRTC 与网络协议：建连和传输要分清

### 02. WebRTC 从打开页面到看到视频，经历什么？P0

**简答：**

1. 业务鉴权，加入房间，创建 PeerConnection 和媒体轨道。
2. 通过自定义信令交换 SDP offer/answer，协商媒体能力和会话参数。
3. 收集并交换 ICE candidates，做连通性检查并选择可用路径。
4. 建立 DTLS，通过 DTLS-SRTP 导出媒体密钥。
5. 媒体以 SRTP/SRTCP 传输，接收端解包、缓冲、解码、渲染。
6. 若使用 DataChannel，建立相应 SCTP 数据通信。

**追问展开：**这是逻辑顺序，实际候选收集、SDP 交换、ICE 检查可以交叠进行，Trickle ICE 允许候选边收集边发送。WebRTC 没有规定业务信令必须使用 WebSocket。

**常见追问：**为何 SDP 成功但没视频？SDP 交换不证明 ICE 已连通，也不证明有发送媒体、收到关键帧或解码成功，应继续看后续阶段。

### 03. SDP 是什么，里面看哪些字段？P0

**简答：**SDP 是会话描述文本，描述媒体类型、编码参数、方向和传输协商信息，不承载实际音视频。

| 字段 | 关注点 |
|---|---|
| m= | 媒体段及相关传输格式 |
| a=rtpmap / a=fmtp | payload type 对应编码及编码参数 |
| a=sendrecv / sendonly / recvonly / inactive | 媒体方向 |
| a=ice-ufrag / ice-pwd | ICE 凭证 |
| a=fingerprint | DTLS 证书指纹，需通过可信信令绑定对端 |
| a=mid / a=group:BUNDLE | 媒体段标识与传输复用关系 |
| a=rtcp-mux | RTP/RTCP 端口复用 |

**容易失分：**认为 payload type 的数字天然代表某个编码。动态 payload type 的含义取决于协商映射。

### 04. ICE、STUN、TURN 分别解决什么？P0

**简答：**

- ICE：收集候选地址，组合候选对，执行连通性检查并选路。
- STUN：帮助发现映射地址，也用于 ICE 检查；不是媒体中继。
- TURN：分配中继资源，在适用路径下转发数据，消耗中继带宽。

| 候选类型 | 含义 |
|---|---|
| host | 本机接口候选；浏览器可能用 mDNS 隐藏本地地址 |
| srflx | 从 STUN 等机制得到的服务器反射映射地址 |
| prflx | 连通性检查过程中发现的对端反射候选 |
| relay | TURN 分配的中继候选 |

**追问展开：**STUN 得到映射，不代表另一端一定能访问。可达性取决于 NAT、过滤、防火墙、网络拓扑等，不应只靠某个 NAT 类型名称下结论。

**排障顺序：**候选是否产生 → 是否经信令送达 → remote description 与候选处理顺序是否正确 → 是否有成功候选对 → TURN 地址、凭证、端口范围与网络策略是否正确。

### 05. DTLS、SRTP 是什么关系？SFU 能看到明文吗？P0

**简答：**WebRTC 常用 DTLS 认证握手并协商密钥，媒体实际用 SRTP/SRTCP 加密和完整性保护；媒体不是全部套在 DTLS 记录中发送。

普通 WebRTC SFU 往往分别终止发布端和订阅端的传输加密，可以访问解密后的编码媒体，再对各跳加密。“WebRTC 加密”不自动等于“服务端不可见的端到端加密”。若要后者，需要额外的媒体端到端加密和密钥设计，并分析对录制、转码、转发可见字段的影响。

**容易失分：**把 TURN 中继、SFU 和解码合成的 MCU 都叫“同一种转发服务器”。

### 06. DataChannel 为什么用 SCTP？P0

**简答：**典型协议栈是 SCTP over DTLS over ICE/UDP，提供消息边界、多流，以及有序/无序、可靠/部分可靠等语义。SCTP 的这些选项让应用能按消息时效选择传输方式。

**追问展开：**无序或部分可靠不等于完全没有排队或阻塞；多个通道可能共享传输、拥塞控制和资源。大消息也可能影响其他消息，需控制大小、发送队列和 bufferedAmount，并考虑实现的消息交织支持。

**场景：**聊天消息与实时状态更新的可靠性需求可能不同；车辆控制的正确性、有效期和失效保护还必须由应用状态机保证。

### 07. 为什么媒体通常用 UDP，而不是全部用 TCP？P0

**简答：**TCP 提供可靠有序字节流，一个丢失字节未补齐时，应用不能按序获得后续字节，可能造成媒体超过播放期限。UDP 允许应用按时效决定重传、FEC、丢弃与码率调整。

**追问展开：**UDP 不等于低延迟保证，更不等于无需拥塞控制。WebRTC 在某些受限网络下也可能经 TURN/TCP 或 TLS 中继；HTTP 媒体也可使用 QUIC。应比较实际路径，不能只背“实时=UDP、非实时=TCP”。

### 08. RTP 的序列号、时间戳、SSRC 分别是什么？P0

| 字段 | 用途 | 典型误区 |
|---|---|---|
| 16 位序列号 | 每发一个 RTP 包递增，用于顺序恢复、缺口检测 | 一个包不一定等于一帧；会回绕 |
| 32 位时间戳 | 媒体采样时刻，按编码规定的时钟频率推进 | 不是 Unix 时间，也不是每包加一 |
| SSRC | RTP 源标识，区分媒体源 | 不宜直接当业务用户 ID |
| payload type | 指示该会话里负载的协商含义 | 数字并非固定对应编码 |
| marker | 含义取决于 payload 格式 | 不能脱离编码规范一律理解为帧末 |

例如：H.264 RTP 通常使用 90 kHz 时钟，30 fps 时理想帧时间戳步长为 3000；同帧分片通常具有相同时间戳。48 kHz Opus 的 20 ms 包对应 960 个时间戳单位。实际包化、帧率和 DTX 等行为仍需按流分析。

**追问展开：**不能用普通整数大小关系直接比较回绕后的序列号，应使用扩展序列号或在有界窗口下的模运算。缺口也可能是乱序，不能首次看到缺口就立刻认定最终丢失。

### 09. RTCP 能提供哪些信息？P0

**简答：**RTCP 提供发送/接收报告和反馈，例如包数、字节数、丢包、抖动、时间映射；扩展反馈还包括 NACK、PLI、FIR 等。它帮助监测与恢复，但不会自动替应用完成所有质量控制。

**深入一点：**

- SR 把某一 RTP 时间戳与发送端的 NTP 格式时间关联，可用于时间映射和同步；不保证发送端时钟本身已准确同步。
- RR 提供接收统计。RTCP interarrival jitter 是包传输时间差变化的平滑估计，原始值单位是对应 RTP 时钟单位，不必然是毫秒。
- 在合适的 SR/RR 交换下可由 LSR、DLSR 等信息估计 RTT，不能把 RTT/2 直接当成精确单向时延。

### 10. WebRTC、RTSP、RTMP、HLS、SIP 怎么区分？P0

| 名称 | 主要职责/特点 | 典型场景 |
|---|---|---|
| WebRTC | 实时通信技术栈，包含协商、选路、安全、媒体/数据传输 | 交互、远程协作、远控视频 |
| RTSP | 媒体会话控制；媒体常用 RTP，可 UDP 或 TCP interleaved | 摄像机拉流、监控 |
| RTMP | 常见为基于 TCP 的媒体传输 | 直播推流、转推 |
| HLS / LL-HLS | 播放列表与媒体分片/部分分片，经 HTTP 分发 | CDN 大规模播放 |
| SIP | 会话建立、修改和结束的信令 | VoIP、部分监控接入 |
| GB28181 | 安防视频联网相关国家标准体系，包含信令、媒体等约定 | 国标监控平台互联 |

**面试回答：**强交互优先研究 WebRTC；大规模分发需考虑 HTTP/CDN 路线；摄像头接入常遇到 RTSP 或 GB28181。延迟取决于编码、缓冲、网络和播放实现，不能给每种协议背一个固定毫秒值。

**追问：**SIP 不负责直接承载视频；RTSP 与 RTP 不是同一层；把 SIP 接通也不代表媒体端口、封装和编码一定正确。

## 3. 编码、封装、时间戳：理解后处理链路

### 11. 编码、封装、协议各管什么？P0

**简答：**编码解决怎样压缩媒体，封装解决怎样组织媒体数据和时间信息，传输协议解决怎样交付或控制会话。

~~~text
H.264 / H.265 / Opus：编码
MP4 / MPEG-TS / FLV：封装格式
RTP / RTMP / HTTP 等：相关传输机制
~~~

它们不是任意自由组合，仍要受封装、协议扩展、服务端和客户端支持限制。文件扩展名也不能单独证明实际编码。

**数字感：**1920×1080 的 8 位 YUV420 原始图像每帧约 3.11 MB，30 fps 约 93.3 MB/s，即约 746 Mb/s，尚未计额外开销。网络传输通常需要压缩，但压缩引入算力和延迟成本。

### 12. I、P、B 帧与 GOP 是什么？P0

**简答：**I 帧主要使用帧内预测，P/B 类图像使用帧间预测；GOP 描述一段图像的预测与组织关系。B 帧常涉及显示与解码重排，低延迟编码常选择不使用 B 帧。

**追问展开：**不要说“所有 I 帧都是 IDR”。IDR 是 H.264 的解码刷新点，后续图像不再引用该 IDR 之前的图像；普通帧内图像不一定切断跨边界参考关系。

GOP 更短通常能缩短等待可随机接入点的时间，也可能提高码率和瞬时峰值；并不是 GOP 越小越好。H.265 还存在 CRA 等随机接入类型，不宜把 H.264 的所有术语原样套用。

### 13. PTS、DTS、time base 怎么解释？P0

**简答：**PTS 是展示时间戳，DTS 是解码时间戳；有重排时两者可能不同。时间戳是按某个 time base 表达的整数，真实秒数需要换算：

~~~text
时间（秒）= timestamp × time_base
~~~

例如 time_base=1/90000，时间戳 9000 表示 0.1 秒，不是 9000 ms。

**追问展开：**输入流、编码器、输出容器的时间基可能不同，FFmpeg 中需要正确 rescale。转封装不能只复制时间戳数值而不换单位。包按解码顺序组织时，PTS 可能因重排而不按包序单调；应分别检查 DTS、PTS 和容器约束。

### 14. NALU、SPS/PPS、Annex B 是什么？P1

**简答：**NALU 是 H.264/H.265 组织编码数据的单元，不等于一个网络包或完整视频帧。H.264 的 SPS/PPS、H.265 的 VPS/SPS/PPS 携带解码所需参数。

Annex B 常用起始码分隔 NALU；另一类表示使用长度前缀，具体由容器与配置决定。RTP 还可能聚合多个 NALU，或把一个大 NALU 拆成多个包；收到 RTP 负载并不意味着可以直接当完整 Annex B 文件写出。

**追问：新订阅者为何黑屏？**可能还没收到参数集与可解码的随机接入图像，也可能是 codec/profile 不兼容、分片丢失或时间戳处理错误。

### 15. 转封装与转码有什么不同？P0

**简答：**转封装保留压缩媒体，改变组织形式和相关元数据；转码通常要解码成原始帧，再用目标编码器编码，成本与延迟更高。

H.265 转 H.264 不能用 -c:v copy。copy 也不保证任意输入都能装进任意输出容器，还要检查编码支持、参数集、时间戳和必要的 bitstream 处理。

**追问：硬件转码是否一定快？**还要看并发、编解码能力、设备间复制、PCIe/显存、驱动、画质与延迟。应测全链路，不只比较某个编码调用耗时。

### 16. 如何降低编码与转码延迟？P1

**简答：**先拆分等待、计算和复制成本，再考虑硬件编码、减少 lookahead/重排、合适的 preset、合理 GOP、码率控制和有界缓冲。

不要把“最快 preset”当作唯一答案：可能增大码率，反过来造成网络拥塞。还需观察关键帧峰值和编码速度是否长期跟得上实时输入。FFmpeg 的 speed > 1x 是特定任务处理能力的参考，不等于实时链路时延小。

### 17. 音视频为什么会不同步？P1

**简答：**来源可能是独立采样时钟漂移、时间戳基准错误、网络缓冲差异、重采样/解码时长变化或渲染调度。接收端需要把各媒体时钟映射到一致的播放时间线。

RTCP SR 等映射信息可提供帮助，但不能忽视源时间戳是否正确和时钟是否同源。长期漂移可能需要重采样、节奏调整或适当丢帧；不能把 RTP 音频时间戳与视频时间戳直接相减，因为它们的时钟频率和起点通常不同。

## 4. SFU 与弱网：岗位最值得深入的部分

### 18. SFU、MCU、Mesh 有什么区别？P0

| 架构 | 服务端工作 | 主要代价 |
|---|---|---|
| Mesh | 端点彼此发送，服务端主要处理信令等 | 多人时端点上行和连接数增加 |
| SFU | 选择性转发已有编码流，做订阅、反馈与适配 | 服务端出网带宽、包处理和会话状态 |
| MCU | 解码、混合或合成、再编码 | 服务端计算与额外处理延迟 |

**简答：**SFU 通常不对每路媒体做完整解码重编码，因此适合多路低延迟转发；但不是无计算成本的 UDP 复制器。

**追问：**SFU 会做 SRTP 处理、RTP/RTCP、包缓存、重传、分层选择、序号映射、pacing、统计和调度；具体能力取决于实现。

### 19. SFU 的带宽怎么估算？P0

**简答：**按实际订阅关系求和，而不是只数在线用户。

假设 N 人各发布码率 r 的一路流，每人订阅其他所有流、且都取相同层，则示例负载为：

~~~text
SFU 入站 ≈ N × r
SFU 出站 ≈ N × (N-1) × r
~~~

N=10、r=2 Mb/s 时，入站约 20 Mb/s，出站约 180 Mb/s；尚未包含协议、重传、冗余等开销。车辆多摄像头场景应按“车数 × 每车流数 × 实际订阅者/层级”计算，不能直接套会议全互订公式。

### 20. Simulcast 与 SVC 的区别？P1

**简答：**Simulcast 通常同时编码发送多个独立质量档位；SVC 在可伸缩编码中组织基础层与增强层。SFU 按接收端网络、显示尺寸和优先级选取可用层，尽量避免自己转码。

**追问展开：**切层需满足解码依赖和可切换点，不能随便拼接任意帧；应加滞回和观察窗口，避免带宽估计小幅波动导致频繁切换。实际可用性取决于编码器、浏览器和 SFU 支持。

### 21. SFU 为什么需要修改序列号、处理反馈？P1

**简答：**SFU 转发给某订阅者的可能只是上游媒体的一部分；切层、过滤和重传会改变下游看到的序列。实现常需维护上下游序列与时间戳映射，让接收端和 RTCP 反馈保持一致。

下游 NACK 应找到对应缓存包或映射到合适的上游请求。不能把多个接收者的反馈不加控制地全部透传，否则可能放大重传或关键帧请求。

### 22. NACK、RTX、PLI、FIR、FEC 怎样区分？P0

| 机制 | 解决的问题 | 成本/限制 |
|---|---|---|
| NACK | 报告具体缺失 RTP 包，请求补发 | 要有缓存，补发到达时还应有用 |
| RTX | RTP 重传的一种封装与流机制 | 需要协商与原包序列关联 |
| PLI | 通知图像丢失导致的解码问题，请求刷新图像 | 编码端通常响应可恢复图像，具体受实现约束 |
| FIR | 请求完整帧内图像刷新，有独立反馈语义 | 不能与 PLI 当作逐字等价 |
| FEC | 发送冗余信息，在一定条件下恢复丢失 | 增加带宽，也可能引入等待 |

**面试简答：**小范围、及时可补的丢包优先考虑 NACK/重传；依赖链损坏时需要图像刷新；在适用条件下用 FEC 减少等待重传，但要算带宽。PLI/FIR 不宜都简化成“协议保证发送 IDR”，实际刷新行为应看编码与实现。

**容易失分：**丢包后频繁请求大关键帧，导致码率峰值、更多拥塞，再次丢包，形成恶性循环。应做限频、合并和按需恢复。

### 23. 拥塞控制与 pacing 分别是什么？P0

**简答：**拥塞控制估计可用传输能力并调整目标速率；pacing 把允许发送的数据更平滑地排到时间线上，避免编码器瞬间产生大帧后形成突发。

带宽估计可结合包到达时间变化、丢包、RTT、ECN 等反馈，具体算法不同。WebRTC 常见实现采用延迟/丢包等信号与 transport feedback，但不能把所有实现都称为同一个固定算法。

**追问：**Transport-wide feedback 使用相应的传输包标识与到达反馈；它不等同于某一路 RTP 媒体的序列号。只有平均码率低于带宽，也可能因关键帧突发和队列产生高尾延迟。

### 24. 为什么缓冲能减少卡顿，却会增加延迟？P0

**简答：**缓冲提供等待晚到数据和吸收处理波动的空间，但数据进入播放前多等了一段时间。系统长期处理速度低于输入速度时，再大的缓冲也只是推迟失效。

~~~text
排队等待时间 ≈ 队列数据量 / 实际处理速率
~~~

例如接收端积压 60 帧，实际每秒处理 30 帧，仅消化已有队列就约需 2 秒；若输入仍为 30 fps，积压不会自行消失。

**追问：**原始视频队列可在满足业务要求时丢旧帧保新；编码依赖帧和 RTP 包不能无差别随意丢，需要编码依赖、层级与恢复策略。jitter buffer 还要区分网络乱序、迟到和最终丢失。

### 25. 弱网优化怎么回答才像工程方案？P0

**简答：**先定义可接受的端到端延迟、画质和恢复要求，再做有控制的适配：

1. 观测吞吐、RTT 趋势、丢包、重传、缓冲与解码耗时，区分拥塞、随机丢包和 CPU 过载。
2. 按拥塞反馈降低目标码率，必要时降分辨率、帧率或切换空间/时间层。
3. 使用 pacing，限制缓存、重传期限和关键帧请求频率。
4. 对重要摄像头/视野保留资源，避免所有流同时抢占。
5. 用相同场景比较改前改后：延迟分布、卡顿、清晰度、带宽与恢复时间。

**容易失分：**只有“加大缓存”“换 UDP”“增加线程”。每个动作都可能引入新的代价，应先说观测到的瓶颈。

## 5. Go 信令服务：会写并发，更要会收尾

### 26. goroutine、线程、GMP 怎么讲？P0

**简答：**goroutine 是 Go runtime 调度的执行单元；G 表示 goroutine，M 表示 OS 线程，P 表示执行 Go 代码所需的调度资源。runtime 把大量 G 调度到一组 M 上运行。

goroutine 栈通常从较小规模开始并可增长，但不是免费资源。大量阻塞、无法退出的 goroutine、过多队列仍会耗尽内存或增加调度成本。GOMAXPROCS 与同时执行 Go 代码的 P 数量相关，不是进程允许创建的线程总数。

### 27. channel、Mutex、RWMutex、sync.Map 怎么选？P0

**简答：**先确定共享状态与所有权，再选机制。房间由单个 goroutine 串行处理消息时，channel 很自然；小范围共享成员表用 Mutex 也很直接。

普通 map 允许无写入时的并发读取，不允许未同步的并发读写。RWMutex 不保证必然比 Mutex 快；sync.Map 适合特定读写模式，不应作为所有业务 map 的替代。

**追问：**“线程安全 map”也不自动保证“查找、判断、更新”整个业务步骤原子，需要把不变量包含在同一同步范围内。

### 28. slice 为什么经常引起并发问题？P0

**简答：**slice 描述符包含底层数组引用、长度、容量。复制 slice 不等于复制元素，多个 slice 可能共享同一数组；append 是否分配新数组取决于容量。

把网络接收缓冲的 slice 放到异步发送队列后又复用原缓冲，可能导致数据被覆盖。可用明确所有权移交、复制或生命周期严格的缓冲池；不能依赖“append 这次刚好扩容了”来保证隔离。

### 29. interface、error、defer 常见追问？P1

**简答：**interface 可理解为动态类型与动态值的组合，包含一个类型为 *T 的 nil 指针时，接口本身未必等于 nil。error 是接口，返回错误应注意 typed nil。

defer 按后进先出执行，参数在登记时求值；在长循环中不断 defer 关闭资源，会把释放推迟到函数返回，可能积压句柄。资源释放应与生命周期对应。

**追问：**错误判断优先使用 errors.Is/As 与合适的错误链，避免单纯匹配字符串；panic/recover 不应替代正常业务错误处理，也不能随意吞掉异常继续使用已损坏状态。

### 30. context 怎么避免 goroutine 泄漏？P0

**简答：**把取消和截止时间沿调用链传递，每个后台任务都设计退出条件，并在连接关闭或请求结束时发起取消。

但 context 取消不会自动打断所有阻塞调用：阻塞网络读可能需要设置 deadline 或关闭连接；向无人接收的 channel 发送，要有 select 取消分支或其他退出机制。最后用 WaitGroup 等等待收尾。

**容易失分：**“传了 context 就不会泄漏”。必须能指出每个 goroutine 在哪些分支结束、由谁释放资源。

### 31. WebSocket 房间服务如何设计？P0

**简答：**连接建立后鉴权与加入房间，读循环解析信令，路由到目标成员，每个连接使用有界发送队列和一个写循环，断连统一清理。

常见 gorilla/websocket 用法约束是一读一写并发；具体控制消息等例外以库文档为准。采用单写循环便于统一处理写超时、心跳和慢客户端。

**关键细节：**

- 不持有全局房间锁执行阻塞网络写。
- 校验消息大小、类型、房间成员权限，不能仅凭客户端声称的 peer ID 转发。
- 慢客户端队列满时有明确策略；关键 offer/answer 不能像过期状态一样静默丢弃。
- 使用连接代次/会话标识，避免旧连接的退出清理误删已经重连的新连接。

### 32. channel 谁来关闭，如何处理背压？P0

**简答：**由生命周期所有者在确认不再有发送者后关闭；关闭表示不再产生新值，不是让接收方随意终止发送方。

向已关闭 channel 发送会 panic；从已关闭且读空的 channel 接收会立即得到零值和 ok=false。多个发送者时要协调退出，不能每个人都 close。

背压要有上限和分级策略：可丢弃的过期状态可合并；可靠业务信令可能需要断开慢连接、重试或重建会话。无限队列只会把网络拥塞转化成内存与延迟故障。

### 33. Gin、gRPC、WebSocket 各放在哪里？P1

**简答：**Gin 可承载 HTTP 管理、鉴权和健康接口；WebSocket 常用于客户端双向信令；gRPC 适合有 schema 的服务间 RPC 与流式调用。

它们都不是 SFU 媒体转发本身。gRPC 的 deadline、状态码、重试和流控需要设计；有副作用的请求不能无脑重试，应考虑幂等键、请求标识和一致性。

**验证工具：**go test -race、pprof、goroutine profile、trace；race detector 只能发现实际执行到的竞态，不证明所有并发路径正确。

## 6. Linux 与 C++：把已有基础讲扎实

### 34. epoll 的 LT/ET、非阻塞、Reactor 怎么讲？P0

**简答：**LT 在条件仍满足时可以重复报告就绪，ET 主要在就绪状态变化时通知。ET 常配合非阻塞 I/O，收到可读事件后循环读取到 EAGAIN。

Reactor 把“就绪事件”和“业务处理”组织成事件分派模型，不代表所有业务都应在事件线程完成。慢磁盘、重计算或锁等待会拖住其他连接，应按成本转移并设定任务队列上限。

**追问：**epoll 事件表示可以尝试 I/O，不保证一定读到完整消息；多线程、关闭和状态变化仍可能导致 EAGAIN 或错误。

### 35. TCP 为什么需要应用层分帧？P0

**简答：**TCP 是有序字节流，不保留应用 write 的消息边界。一次 recv 可能得到半条、多条或组合后的内容，需要长度字段、分隔符或协议语法来解析。

send 也可能只发送部分数据，非阻塞下还会 EAGAIN。应保存发送进度，按需关注 EPOLLOUT，不能每次都假定整包写完；收到 EOF 时还要正确处理已收数据和连接状态。

**追问：**UDP 保留报文边界，但接收缓冲不足可能截断，不代表“永不丢包”。

### 36. C++ RAII、智能指针与回调生命周期？P0

**简答：**RAII 用对象生命周期管理 socket、锁、缓冲等资源；唯一所有权优先考虑 unique_ptr，需要共享所有权时才用 shared_ptr。

shared_ptr 的引用计数管理不等于被指向对象线程安全。回调捕获 shared_ptr 可能形成环或延长连接生命周期，可用 weak_ptr 配合 lock 检查；只捕获裸 this 则需保证回调执行前对象不会销毁。

**追问：**异步媒体回调中的 buffer 归谁、何时复用，比“用了智能指针”更值得说明。

### 37. 零拷贝与缓冲池怎样回答？P1

**简答：**先指出哪一次复制：用户/内核、进程间、解码器/编码器、CPU/GPU，优化才有明确对象。池化减少分配频率，但会引入所有权和内存保留问题。

sendfile 适合某些文件到 socket 的路径，不是所有实时 SRTP 转发的直接替代。加密、协议改写、设备间传递可能仍需处理；“零拷贝”也不意味着 CPU、缓存和生命周期成本为零。

### 38. 多线程为什么未必提升吞吐？P0

**简答：**可能被锁竞争、内存带宽、频繁复制、缓存失效、上下文切换或网卡带宽限制。先做 CPU profile 和队列观测，再决定线程模型。

连接/流归属清晰的分片或事件循环模型，可减少跨线程共享；但热点房间、不均衡流量和单流瓶颈仍需单独处理。比较方案必须固定机器、负载、编译配置和测试时长。

## 7. 时间同步与质量指标：你的项目优势

### 39. 端到端延迟怎样分解？P0

**简答：**从相机曝光/采集到显示器呈现的 glass-to-glass 延迟，可拆成：

~~~text
采集/等待 + 编码 + 发送排队 + 上行网络
+ SFU 处理/排队 + 下行网络 + 抖动缓冲
+ 解码 + 渲染/显示等待
~~~

定义必须明确：从“收到压缩包”开始计时不是完整 glass-to-glass；渲染提交时间也不一定等于屏幕真正显示。

**追问：**平均延迟低仍可能有严重尾部卡顿，需看 P50/P95/P99、最大值、卡顿时长、样本数与窗口，而不只报一个平均数。

### 40. 两台机器的时间戳能直接相减吗？P0

**简答：**只有明确时钟关系才有意义。接收端减发送端的值，通常同时包含真实单向时延、时钟 offset、drift 与打点误差。

~~~text
观测差值 ≈ 真实单向时延 + 两端时钟偏差 + 测量误差
~~~

同机阶段耗时优先用单调时钟；跨机要评估 NTP/PTP/GNSS 同步质量，记录同步状态与误差预算。不能直接把两台机器各自 CLOCK_MONOTONIC 的绝对读数相减。

**与你的工程连接：**280 MHz 对应约 3.57 ns/tick，是计数分辨率，不等于全链路绝对同步精度。PPS 输入、捕获、软件对齐、线路延迟和参考源质量都会影响实际误差。

### 41. NTP、PTP、GNSS/PPS、RTCP SR 怎么区分？P0

| 机制 | 主要作用 | 需要说明的边界 |
|---|---|---|
| NTP | 网络时间同步 | 受路径不对称、软件打点、网络状态影响 |
| PTP | 精密时间同步协议 | 硬件时间戳与网络设备支持很关键，精度依部署而定 |
| GNSS + PPS | 提供时间参考与秒边沿 | 单独 PPS 通常不含完整日期/秒号，需配套时间信息 |
| RTCP SR | 关联媒体 RTP 时钟与发送端时间 | 不自动把多台主机同步到可信 UTC |

**追问：**HOLDOVER 表示参考丢失后按本地时钟维持，不代表仍有相同绝对同步质量；应让上层看到同步状态和不确定度，而不是隐藏异常。

### 42. 丢包率、jitter、RTT、卡顿怎么一起看？P0

**简答：**它们不在同一层。网络到包不等于成功解码，成功解码不等于及时显示。应把每层计数和耗时沿同一 stream/session 标识关联。

建议同时记录：

- 发送/接收码率、包数、乱序、最终丢包、NACK/RTX/FEC 数量。
- RTT、延迟趋势、实际候选路径类型、切层事件。
- 帧采集、编码、接收、解码、显示计数与队列等待。
- 关键帧请求、解码错误、冻结持续时间及恢复时间。

不要因网络丢包很低就排除编码/解码过载；也不要把应用没来得及读 socket 导致的内核丢包全部归因于公网。

## 8. 云端部署与稳定性

### 43. SFU 为什么不能简单复制多个 Pod？P1

**简答：**媒体会话有状态，已建立的 ICE/DTLS、订阅、重传缓存和拥塞控制状态通常绑定具体实例。增加副本不会自动迁移现有会话。

需考虑房间/会话调度、节点地址发布、媒体端口暴露、负载、TURN 路径和下线排空。负载不应只看 CPU，还要看出网、包率、订阅流和队列。控制面状态共享也不等于传输会话已无状态。

### 44. readiness、liveness、startup probe 怎么用？P1

**简答：**readiness 控制是否准备接收相应流量，liveness 用于判断是否需重启，startup probe 保护较慢启动过程。

对 RTC 节点，readiness 变化不能保证已建立的 UDP 媒体会话被迁走。优雅下线应先拒绝新会话，保留或有序结束旧会话，再退出；不要让短暂负载峰值触发大面积重启。

### 45. 压测与观测需要哪些可复现条件？P1

**简答：**固定软件版本、机器、网络拓扑、房间数量、每房人数、发布/订阅关系、编码、分辨率、码率、弱网模型和持续时长，再比较资源与质量。

指标包括建连成功率/耗时、首帧时间、端到端延迟分布、卡顿、恢复时间、CPU、RSS、GC、goroutine、带宽与包率。

Prometheus 标签避免直接放无限增长的 room ID、peer ID、完整 URL；这类细粒度上下文更适合日志或追踪，防止高基数把监控本身拖垮。日志可带关联标识，但不要记录完整凭证和敏感会话材料。

## 9. 排障与业务场景

### 46. “画面一直流畅，但越来越延迟”，怎么排？P0

**简答：**优先怀疑输入大于处理能力或播放时间线追赶失败，查各级队列长度、最老数据年龄、输入/输出速率，而不是只看 FPS。

排查顺序：采集队列 → 编码器/lookahead → socket/pacer → SFU 出队 → 接收抖动缓冲 → 解码 → 渲染。

若某队列持续变长，查该级 CPU、锁、下游背压与时间戳。设置有界队列及符合依赖关系的丢弃/降级策略，并验证端到端尾延迟是否下降。重启后暂时恢复只能说明状态或积压被清空，不能作为最终修复。

### 47. “连接成功但黑屏”，怎么排？P0

**简答：**先确认“成功”指信令、ICE、DTLS 还是应用状态，然后按计数定位：

~~~text
采集帧是否增长？
  → 编码帧是否增长？
  → 发送 RTP 字节/包是否增长？
  → SFU 入站、订阅出站是否增长？
  → 客户端收包、解码帧、显示帧是否增长？
~~~

有收包无解码：查编码协商、参数集、关键帧、分片重组、SRTP/解码错误；有解码无显示：查渲染、元素绑定、播放策略、线程阻塞。还要排除摄像头本来输出黑画面。

### 48. “相机约几秒后停帧，但 MCU 仍有触发”，怎么回答？P0

**这是你当前项目可用的排障案例，根因尚未确认，不要讲成已修复。**

我会分层验证：

| 层级 | 证据与判断 |
|---|---|
| MCU PB10 | 同时测周期、脉宽、幅度；仅有 10 Hz 不代表波形符合要求 |
| 电平转换后相机 SYNC | 检查相机实际收到的 1.8 V 基准信号、边沿、共地与反相 |
| MODE、LEDEN、曝光、STRB | 确认模式优先关系；STRB 需先启用才可用来辅助判断响应 |
| V4L2/UVC | 看 DQBUF/QBUF、帧序号、select 错误、USB 内核日志 |
| ROS/RViz | 区分采集停止、发布停止与界面显示旧帧；界面刷新率不是相机帧率 |

**当前已知边界：**本地源码预期 PB10 高 4 ms、低 96 ms；测试截图曾报告高低各约 50 ms，需先核对实测方法和固件版本。比较中断超时是已识别风险，尚不能认定为那次停帧根因。

万用表直流读数也不能代替脉冲测量：3.3 V、4% 占空比的理想平均值约 0.132 V，接近零不证明无脉冲。下一步应在停帧时同步观察转换器前后波形，并检查相机响应和 USB 输出。

**岗位连接：**它体现的是逐层计数、时间关联和证据排除方法；不是声称已有生产级 RTC 排障经历。

### 49. 远程驾驶的控制消息，可靠送达就够了吗？P0

**简答：**不够。必须鉴权、鉴别会话、处理序列/去重、有效期、应答、失联与重新授权。旧会话迟到的控制消息不能因“终于收到”就执行。

媒体、信令、车辆控制的职责与故障边界要明确。视频可以按策略降画质、丢弃过期数据，控制指令需要由车辆安全设计定义顺序、时效与失效行为。不同命令类别也可能有不同语义，不能统一无条件丢弃所有乱序数据。

共享网络时要防止媒体拥塞拖垮控制消息；DataChannel 的可靠选项不代替这些业务机制。跨机有效期依赖时钟关系，本地失联超时应用单调时钟。具体停车、减速等策略由安全方案和验证决定，不能面试时随意承诺某个阈值。

### 50. 录制、转推、回放为什么不是“把收到的包写文件”？P1

**简答：**先区分输入是 SRTP、RTP 负载还是完整编码帧；录制要处理解密、重排、去包化、参数集、时间基、音视频同步和容器索引，不能把网络包原样拼成 MP4。

没有改变编码需求时可考虑转封装；目标协议或播放器不支持原编码时才需要相应转码。转推还要处理连接中断、输出背压和重新接入后的可解码起点。

**追问展开：**回放 seek 常需从合适的随机接入点开始，再解码到目标展示位置；录制中途发生断流、时间戳重置、编码参数变化时，应定义分段或时间线衔接规则。长时录制可以评估分段或 fragmented MP4 等形式，但仍要分析索引、异常退出、存储速度与文件可恢复性。

**容易失分：**声称“SFU 本来不解码，所以录制也完全不用处理编码结构”。转封装可以不重编码，但仍要正确理解包化、参数和时间信息。

## 11. 常用工具与命令：知道它们证明什么

以下是学习环境的示例，**本次没有在 NUC 上执行，也不表示已经完成相应实验**。路径、端口、工具版本和权限按实际环境调整；不要与正在占用相机的进程同时启动另一份采集程序。

### 11.1 FFmpeg / ffprobe

~~~bash
# 检查输入文件的编码、分辨率、时间基、流信息。
ffprobe -v error -show_streams -show_format input.mp4

# 查看视频包的 PTS、DTS、时长和标志，限制读取前 5 秒。
ffprobe -v error -select_streams v:0 -read_intervals "%+5" \
  -show_packets -show_entries packet=pts_time,dts_time,duration_time,flags \
  -of csv=p=0 input.mp4

# 本地生成 8 秒练习文件；需构建包含 libx264。
# 这些参数用于观察低重排配置，不证明实际网络链路低延迟。
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -t 8 \
  -c:v libx264 -preset veryfast -tune zerolatency \
  -bf 0 -g 30 -pix_fmt yuv420p rtc_practice.mp4

# 练习 H.265 输入解码、再编码为 H.264；不能把 copy 当作转码。
ffmpeg -i input_h265.mp4 -map 0:v:0 -an \
  -c:v libx264 -preset veryfast -tune zerolatency \
  -bf 0 output_h264.mp4
~~~

FFmpeg 不同构建支持的编码器、硬件接口不同，先看 ffmpeg -encoders。媒体工具显示的 fps、speed、bitrate 不是同一个指标。

### 11.2 网络与系统

~~~bash
ss -uapn                 # UDP socket 与进程；部分进程信息需要相应权限
ss -tinp                 # TCP 连接与统计
ip -s link              # 网卡收发和错误计数
top -H -p <PID>          # 某进程线程负载，替换 PID
pidstat -p <PID> 1       # CPU、任务信息；需安装 sysstat
journalctl -k -f         # 内核日志，适合观察 USB/驱动事件
~~~

抓包优先限定接口、主机、端口和时长。SRTP 加密负载不能仅靠普通抓包还原为视频；在加密情况下仍可结合端点统计和可见元信息定位。抓包的时间戳精度与打点位置也影响结论。

浏览器可查看 chrome://webrtc-internals，结合 getStats 观察 candidate pair、RTT、码率、包/帧计数与解码信息；指标字段和支持情况依实现而异。

### 11.3 Go 诊断

~~~bash
go test ./...
go test -race ./...
go test -bench=. -benchmem ./...
~~~

pprof 的 CPU、heap、goroutine、block/mutex profile 各看不同问题，需按应用配置采集。诊断接口只暴露在受控环境，避免把敏感运行信息直接开放公网。

### 11.4 你的相机排障可用工具

~~~bash
v4l2-ctl --list-devices
v4l2-ctl -d /dev/videoX --list-formats-ext
v4l2-ctl -d /dev/videoX --list-ctrls
~~~

videoX 必须先识别，USB 相机可能暴露多个节点；相机控制值还可能被采集程序启动时改写。说明书定义的曝光/触发控制不一定符合通用 UVC 名称的日常语义，应读回并按设备资料解释。
