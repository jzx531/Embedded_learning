简短回答：**和“物理硬件”是强绑定，和“驱动代码”是弱绑定（解耦的）。**

你手写笔记里这两行：

```dts
interrupt-parent = <&gpio5>;
interrupts = <1 flag>;
```

### 1. 对硬件：强绑定，改不了

这两行描述的是**板上真实的电气连接**：

- `&gpio5` → 按键的 INT 线实际接到了 SoC 的 GPIO5 这个 bank；
- `1` → 实际接的是这个 bank 里的第 1 号引脚（GPIO5_IO1）；
- `flag` → 硬件上按键/外部芯片是低电平有效、还是上升沿有效，这是电路决定的。

所以：

> 换板子、改走线 → 这两个值**必须改**，否则中断永远不来，或者来的是别的引脚。

这一层是**物理事实**，设备树只是把它“记录下来”，不能凭空改变。

### 2. 对驱动：弱绑定，已解耦

关键在于：驱动里**不写 `gpio5`、不写 `1`**，而是写：

```c
irq = platform_get_irq(pdev, 0);
request_irq(irq, isr, ...);
```

内核内部做了两层翻译：

```text
设备树: gpio5 + 引脚1 + flag
        ↓ irq_domain / gpiochip 的 irqdomain 映射
Linux 虚拟中断号 virq（比如 187）
        ↓
驱动只用 virq，不知道它来自 gpio5 还是 GIC 还是 PCIe
```

所以：

- 硬件从 GPIO5_IO1 挪到 GPIO3_IO7 → **只改设备树，驱动一行不动**；
- 换成另一颗 SoC，中断控制器从 GPIO 换成专用 EIC → **驱动还是一行不动**；
- 甚至用 ACPI 的平台（x86），驱动同样用 `platform_get_irq()`。

这就是设备树存在的意义：**把“硬件描述”从代码里搬出去，让同一份驱动跑在不同板子上。**

### 3. 但有几个“隐性绑定”要注意

设备树不是万能的，下面这些仍然是绑定关系：

| 项目 | 是否绑定 | 说明 |
|---|---|---|
| 引脚号 / 控制器 | 强绑定 | 电路决定，必须写对 |
| `flag` 触发类型 | 强绑定 | 由外部电路/芯片决定 |
| `#interrupt-cells` | 强绑定 | 决定 `interrupts` 有几个 cell，写错解析失败 |
| `compatible` | 半绑定 | 决定用哪个驱动，属于“约定” |
| 中断号数值本身 | 不绑定 | 驱动拿到的是 virq，每次启动可能都不同 |

另外：**`interrupts` 只描述“中断怎么来”，不描述“引脚怎么复用”**。引脚复用要靠 `pinctrl`，如果 pinctrl 没配对，GPIO 没被设成输入/中断功能，中断一样不触发——这也是很多人踩的坑。

### 4. 一个直观类比

```text
设备树 = 接线图（硬件事实，换板必改）
驱动   = 用电器（只认“插座”，不认线从哪来）
irqdomain = 电工，把“哪根线”翻译成“几号插座”
```

### 一句话总结

**设备树里的中断定义与硬件是强绑定（必须如实反映电路），但与驱动是解耦的（驱动只通过 `platform_get_irq()` 拿虚拟中断号，硬件变了改 DTS 即可）。**
